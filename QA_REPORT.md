# QA-отчёт: «Цифровой деканат AI High School»

Дата проверки: 20.11.2026. Коммит: `e69e1d1` (main). Окружение: Arch Linux, Node 24, `pnpm dev` (API на PGlite + Vite), встроенный браузер, ширина 360×780 и десктоп.

## 1. Итог

Прототип работает. Все пять разделов обязательного ядра есть: вход, профиль, расписание с изменениями, успеваемость с прогнозом, заявки со статусами и уведомления. Сквозной сценарий «войти → расписание → оценки → подать заявку → сотрудник меняет статус → студент видит уведомление и справку с QR» прошёл без ошибок на 360 px. Безопасность сделана добросовестно: при подмене id в URL и API чужие данные не открываются (404), staff-API для студента закрыт (403), пароли хешируются argon2id, сессия в httpOnly-cookie, секретов в коде и бандле нет. Нашёл один Major-баг: двойной клик по «Отправить» создаёт две заявки. Ещё один Major-пробел — в репозитории нет README с тестовыми аккаунтами и инструкцией запуска. Остальное — мелочи. Публичный деплой я не проверял: ссылки на него у меня нет. **Предварительная оценка: 7,75 из 10** (K1 8, K2 8, K3 7, K4 8). Это мнение одного эксперта, а не среднее по жюри.

## 3. Найденные баги

### Blocker / Critical

Не найдено.

### Major

**M1. Двойной клик по «Отправить» создаёт две одинаковые заявки** (R10, K3)
- Шаги: войти как `student` → «Заявки» → «Новая заявка» → «Выписка с оценками» → «Далее» → комментарий → «Далее» → дважды быстро кликнуть «Отправить».
- Ожидаемо: одна заявка.
- Фактически: две заявки с разницей 13 мс (`945df4c5-…` в 01:56:25.760Z и `3329bfa8-…` в 01:56:25.773Z), обе видны студенту и в очереди сотрудника.
- Код: `apps/web/src/features/requests/NewRequestWizard.tsx:78`. Проверка `if (!type || create.isPending) return;` читает `isPending` из замыкания текущего рендера, и до перерисовки второй клик её проходит. `disabled={create.isPending}` (строка 183) тоже применяется только после рендера. На сервере идемпотентности нет.

**M2. В репозитории нет README** (R25, K3, сдача)
- Шаги: открыть корень репозитория.
- Ожидаемо: README со ссылкой на прототип, тестовыми аккаунтами, инструкцией запуска и описанием проекта. Это запланировано в `ROADMAP.md:79`.
- Фактически: `README.md` отсутствует. Жюри, открыв репозиторий по ссылке, увидит только список файлов. Логины и пароли тестовых аккаунтов есть только в коде сида.

**M3. Изменения в расписании не доходят до студента, пока он не откроет расписание** (R6, R13)
- Шаги: войти как `student` в пятницу 20.11 → главная → уведомления.
- Ожидаемо: сегодняшняя отмена «Теория вероятностей, 10:45» заметна на главной или пришла уведомлением.
- Фактически: на главной в «Следующей паре» отменённая пара просто пропущена, без пометки. В уведомлениях есть только перенос NLP. Отмена 20.11, замена аудитории 19.11 и замена преподавателя 28.11 видны лишь в самом расписании.
- Код: уведомления о расписании создаются только в сиде (`apps/api/src/db/seed/data.ts`), из данных о `change` они не выводятся.

### Minor

**m1. Все справки печатаются с одним и тем же текстом; «Выписка с оценками» не содержит оценок** (R10)
- Шаги: заявка «Выписка с оценками» → сотрудник «Готово» → «Справка для печати».
- Ожидаемо: в выписке оценки, в справке о стипендии размер стипендии.
- Фактически: у всех 4 типов текст «…подтверждает, что указанное лицо обучается в вузе». Код: `apps/web/src/features/certificates/CertificatePage.tsx:98`.

**m2. Через API можно отклонить заявку без причины** (R11)
- Шаги: под `staff` выполнить `POST /api/staff/requests/:id/status` с телом `{"status":"rejected"}`.
- Ожидаемо: 400, как и в UI («Напишите причину отказа — её увидит студент»).
- Фактически: 200, студент получает отказ без объяснения. Код: `packages/contract/src/staff.ts`, `ChangeStatusInputSchema`. Причина обязательна только в UI.

**m3. На странице справки по отклонённой заявке обещают, что справка появится** (R11)
- Шаги: открыть `/requests/<отклонённая>/certificate`.
- Фактически: «Справки пока нет. Она появится, когда деканат отметит заявку как готовую», хотя заявка уже закрыта отказом.

**m4. «Средний балл 60» считается и по дисциплинам без итога** (R9)
- Шаги: `/grades`.
- Фактически: (37 + 47 + 52 + 71 + 93) / 5 = 60. Сюда входят частичные баллы двух несданных экзаменов, поэтому цифра занижена и легко неверно понимается. Подписи «по текущим баллам» нет.

**m5. На любую ошибку сервера пишется «Проверьте интернет»** (K4)
- Шаги: открыть `/schedule?view=week&week=9999-12-27` (API отвечает 500).
- Фактически: «Не получилось загрузить. Проверьте интернет и попробуйте ещё раз». Интернет работает, ошибка на сервере. Код: `apps/web/src/ui/states.tsx:83`.

**t1. `GET /api/me/schedule?week=9999-12-27` → 500** вместо 400. Конец недели уходит в 10000 год (`apps/api/src/lib/moscow-time.ts:41`). Обычный пользователь сюда не попадёт.

## 4. Нефункциональные замечания

**UX и понятность.** Навигация из 5 пунктов и бейджи непрочитанного понятны. Мастер заявки из 3 шагов со сроками («обычно 1–2 рабочих дня») и экраном проверки, после отправки сразу открывается карточка заявки с подтверждением. Не хватает поиска и фильтра в длинных списках уведомлений и заявок, но при текущем объёме данных это некритично.

**Адаптивность.** 360 px: горизонтального скролла нет ни на одном из 10 проверенных экранов. На десктопе раскладка двухколоночная, с боковым меню. На реальных устройствах не проверял.

**Доступность.** Есть skip-link «Перейти к содержимому». Поля связаны с `<label>`, подсказки через `aria-describedby`. Бейджи озвучиваются как «Уведомления, 2 непрочитанных». Радиокнопки типов заявки подписаны. Контраст покрыт тестом `a11y-contrast.node.test.ts`. Скринридером не проверял.

**Производительность.** Весь JS — один чанк 581 кБ (gzip 176 кБ), Vite предупреждает при сборке. Для мобильного 3G стоит разбить по роутам (`React.lazy`). Lighthouse не запускал.

**Безопасность.**
- Сильные стороны: id только из сессии, ответы 404 вместо 403, UUID, argon2id, в БД хранится SHA-256 токена сессии, cookie `HttpOnly; SameSite=Lax` (+`Secure` в проде), rate-limit входа (10 попыток / 15 мин, 11-я → 429, проверено), единое сообщение об ошибке входа, Zod на каждом входе. XSS-строка `<img src=x onerror=alert(1)>` и SQL-строка `'; DROP TABLE` в комментарии сохранились и отрисовались как текст, ничего не выполнилось. Caddy ставит `nosniff` и `X-Frame-Options DENY`.
- Замечание: rate-limit берёт адрес из последнего значения `X-Forwarded-For` (`auth/routes.ts:24`). В dev без прокси заголовок подделывается: со сменой `X-Forwarded-For` лимит не срабатывает (проверено). В проде защиту даёт Caddy, но на развёрнутом стенде я это не проверял.
- Замечание: id в сиде детерминированные (`seedId` = sha256 от ключа, `seed/data.ts:10`), то есть по открытому коду их можно вычислить. Утечки это не даёт, потому что проверка владельца работает (R22), но формально нарушает принцип «id не угадываются».
- Нет заголовка `Content-Security-Policy`. Для прототипа некритично.

**Качество кода и архитектуры.** Чистое разделение `contract` / `api` / `web` через Zod-контракт. Сервисы небольшие, с комментариями «почему». Гонки учтены: условный UPDATE при смене статуса, `onConflictDoNothing` при выпуске справки. Тесты: contract 49, api 109, web 191, всего 349, все зелёные. E2E-тестов на Playwright нет, хотя скрипт `pnpm e2e` упомянут в `CLAUDE.md`.

**README и запуск.** README нет (M2). Инструкция запуска есть в `CLAUDE.md` и `.env.example`. `pnpm install && pnpm dev` поднимается без Docker и сама наполняет БД демо-данными.

## 5. Сильные стороны

- Безопасность доступа проверена руками по всем ресурсам с id, и каждый кейс закрыт тестом «чужой → 404».
- Калькулятор «Что нужно набрать» под три цели: честная, полезная идея, которая отвечает на вопрос «как у меня дела».
- Полный цикл заявки: студент → очередь сотрудника → уведомление → справка для печати с QR → публичная проверка, где показаны только инициалы.
- Демо-режим продуман для жюри: общий аккаунт можно сбросить, и сброс трогает только свои данные.
- Процесс работы с ИИ прозрачен: правила, skills, хук, субагент-ревьюер, журналы с реальными ошибками ИИ.
- Состояния интерфейса проработаны: загрузка, пусто, ошибка, 404, «справки пока нет».

# QA-отчёт: «Цифровой деканат AI High School» (повторная проверка)

Дата: 20.11.2026. Коммит: `685a425` (`main` = `origin/main`). Перед проверкой локальный `main` был перемотан fast-forward с `9e65279`: в нём не хватало трёх уже смерженных PR (#63–#65).

Окружение: Arch Linux, Node 26. Стенд — **прод-сборка** (`node apps/api/dist/index.js` раздаёт `apps/web/dist`) на чистой базе PGlite, засеянной при старте. Встроенный браузер, 360×780 и десктоп, светлая и тёмная темы. Аккаунты `student`, `student2`, `staff` взяты из README.

## 1. Итог

Прототип зрелый. Обязательное ядро реализовано полностью, сквозной сценарий «вход → расписание → оценки → заявка → сотрудник меняет статус → уведомление → справка с QR → публичная проверка» проходит на 360 px без ошибок. Шесть из семи находок прошлого отчёта исправлены, и я перепроверил это руками, а не по коммитам. Двойной клик больше не создаёт дубль, README есть, отказ без причины API не принимает, изменения расписания приходят уведомлениями. Добавились даты экзаменов, долги прошлых сессий с кнопкой «Подать на пересдачу» и выписка с таблицей оценок. Безопасность доступа к данным держится по всем ресурсам с id. Остались две серьёзные проблемы. Первая: прототип ещё не развёрнут (в README: «ссылка появится после деплоя»). Вторая: демо-данные считаются от момента первого запуска, поэтому за неделю судейства расписание и уведомления разойдутся (Major, воспроизведено скриптом). **Предварительная оценка: 8,0 из 10** (K1 9, K2 8, K3 7, K4 8). Это мнение одного проверяющего. K3 ограничен тем, что публичную ссылку проверить нельзя.

## 3. Найденные баги

### Blocker / Critical

Не найдено.

### Major

**M1. Демо-данные расходятся со временем: уведомления описывают изменения, которых нет в расписании** (R6, R13, K3)

- Причина. Сид строит все даты от `now` в момент первого запуска и запускается только на пустой базе (`apps/api/src/index.ts:14`). Демо-сброс, к которому README прямо отправляет жюри, пересоздаёт заявки и уведомления от **текущего** `now`, а пары в расписании не трогает (`apps/api/src/db/seed/reset.ts:19`).
- Шаги (скрипт на PGlite в памяти через `createApp` с подставным временем): засеять базу на пятницу 20.11 12:00 МСК → в среду 25.11 войти как `student` → `GET /api/me/schedule` и `GET /api/me/notifications` → `POST /api/me/demo-reset` → повторить запросы.
- Ожидаемо: уведомления об изменениях совпадают с тем, что видно в расписании.
- Фактически:
  - до сброса неделя 23–29.11 содержит одно изменение (28.11, замена преподавателя), а непрочитанным висит «пара 20.11 отменена» о прошлой неделе;
  - после сброса приходят 4 **новых** уведомления: «пара 27.11 отменена», «замена аудитории 26.11», «Перенесено с 25.11… Новое время: 24.11», «замена преподавателя 05.12». **Ни одного из этих изменений в расписании нет**, там по-прежнему только замена 28.11.
- Последствия: если деплой будет 21–22.11, то с понедельника 23.11 (в разгар судейства до 28.11) расписание жюри перестанет показывать изменения в текущей неделе, а сброс сделает уведомления ложными.
- Связанное наблюдение: локальная dev-база `apps/api/.pglite`, засеянная до миграций `0002`/`0003`, так и осталась без дат экзаменов и долгов. Сид не перезапускается на непустой базе, поэтому повторный деплой на старую базу новых демо-данных тоже не получит.

**M2. Прототип не развёрнут, ссылки нет** (R14, K3)

- Шаги: открыть `README.md`.
- Ожидаемо: публичная ссылка, которая открывается из России без VPN до 28.11.
- Фактически: `README.md:7` — «**Прототип:** ссылка появится после деплоя». По `FIX_PLAN.md` задача #20 «Деплой на ВМ» открыта (`needs-human`). До дедлайна (22.11 23:59) осталось около двух суток. Прод-стек (`docker compose`) я не поднимал, поэтому пройдёт ли деплой, не проверено.

**m2. «Закрыть сессию: достижимо» не учитывает долг прошлой сессии** (R9)

**m3. В выписку попадают незакрытые дисциплины с промежуточными баллами** (R10)

- Шаги: заявка «Выписка с оценками» → сотрудник «Готово» → «Справка для печати».

## 4. Нефункциональные замечания

**UX и понятность.** На главной собрано всё на сегодня. Нижняя навигация из 5 пунктов, у бейджей есть текст для скринридера («Уведомления, 4 непрочитанных»). Мастер заявки показывает сроки и валидирует на месте. После отправки сразу открывается карточка с подтверждением. Из долга можно в один клик перейти к заявлению. Кабинет сотрудника: фильтры по статусам, понятное «Заявка закрыта — статус больше не меняется», «Заявка не найдена» для неверного id.

**Адаптивность.** 13 экранов на 360 px без горизонтального скролла. На десктопе боковое меню и двухколоночная главная. Реальные устройства не проверялись.

**Доступность.** Skip-link, подписи полей через `<label>`, ошибки в `role="alert"`, статусы передаются текстом и иконкой, а не только цветом, при смене шага мастера фокус переходит на заголовок. Есть тест контраста (`a11y-contrast.node.test.ts`). Скринридером не проверял.

**Производительность.** Страницы теперь грузятся лениво (`GradesPage-*.js`, `StaffPage-*.js` и др.), но стартовые чанки `index` 272 кБ и `ui` 252 кБ (gzip 87 + 77 кБ) всё равно грузятся сразу. Для 3G это ощутимо. Lighthouse не запускал.

**Устойчивость к сбоям.** При остановленном сервере экраны с данными показывают «Не получилось загрузить. Проверьте интернет и попробуйте ещё раз.» с кнопкой «Повторить». Расписание после перезагрузки открывается из кэша service worker, как и обещает PWA.

**Безопасность.**

- Хорошо: id только из сессии, ответ 404 вместо 403 на чужое, UUID, argon2id, в БД хранится SHA-256 токена сессии, cookie `HttpOnly; SameSite=Lax` (+`Secure` в проде), Zod на каждом входе, `safeNext` защищает `?next=` от открытого редиректа (`apps/web/src/app/guards.tsx:18`). Строки `<script>alert(1)</script><img src=x onerror=alert(2)>` выводятся как текст в карточке заявки, у сотрудника и в справке.
- Rate-limit: 11-я неудачная попытка → 429 (проверено). Ключ — последнее значение `X-Forwarded-For` (`auth/routes.ts:24`): без прокси заголовок подделывается, и с новым значением лимит обходится (проверено). В проде защиту даёт Caddy, но это не проверено.
- Id в сиде детерминированные (`seedId`), их можно вычислить по открытому коду. Утечки нет, потому что проверка владельца работает.
- Нет `Content-Security-Policy`. Для прототипа некритично.

**Качество кода и архитектуры.** Чистая граница `contract / api / web`, каждая фича идёт двумя PR (контракт, потом реализация). Гонки учтены: условный UPDATE статуса, `onConflictDoNothing` при выпуске справки. Тесты: contract 50, api 125, web 206 — **381 пройдено, 0 упало**. `pnpm typecheck`, `pnpm lint` (171 файл, без замечаний) и `pnpm build` зелёные. E2E на Playwright нет, хотя `CLAUDE.md` и `.claude/rules/frontend-ui.md` их ожидают.

**README и запуск.** README хороший: аккаунты, сценарий на 2 минуты, «как устроены вход и защита» простыми словами, запуск без Docker. Нет ссылки на прототип (M2). Нет предупреждения, что старую `.pglite` нужно удалить, чтобы получить новые демо-данные.

## 5. Сильные стороны

- Доступ к чужим данным закрыт по всем ресурсам с id, это проверено вручную и в автотестах.
- Учёба собрана вокруг вопроса «что мне делать»: ближайший экзамен, сколько баллов нужно до цели, долг с кнопкой пересдачи.
- Полный цикл документа: заявка → очередь сотрудника → уведомление → справка для печати → QR → публичная проверка с минимумом данных. Выписка — снимок на дату выдачи.
- Продуманы детали для жюри: README со сценарием, сброс демо-данных только своего аккаунта, дисклеймер на каждом документе.
- Команда сама работает с ошибками ИИ: `FIX_PLAN.md` сверяет каждую находку QA с кодом и спорит там, где она спорна.

# Модуль api

Hono + Drizzle. Правила доступа описаны в `security.md`, они обязательны.

## Структура
- `src/modules/<домен>/`: `routes.ts` (Hono-роутер), `service.ts` (логика и запросы к БД), `*.test.ts`. Роуты тонкие, логика живёт в сервисе.
- `src/auth/`: логин и логаут, сессии, middleware `requireAuth` и `requireRole`.
- `src/db/`: `schema.ts` (Drizzle, `pg-core`), `migrations/` (drizzle-kit), `seed/`, `client.ts` (PGlite, если `DATABASE_URL` не задан, иначе Postgres).
- Импорты из `apps/web` запрещены, общие типы берём только из `@aihs/contract`.

## Запросы и ответы
- Вход валидируется через `zValidator` по схеме из контракта. Ответ собирается в форме DTO контракта.
- Ошибки отдаём в одном формате `ApiError` через общий error-handler. Стек наружу не уходит.
- Коды ответа: 400 — невалидный вход, 401 — нет сессии, 403 — не та роль, 404 — не найдено или чужое, 409 — конфликт, 429 — rate-limit.
- Схема БД меняется только через миграцию (`drizzle-kit generate`). Сгенерированные SQL-файлы руками не правим.

## Сид и время
- Сид детерминированный и идемпотентный: повторный запуск даёт то же состояние. Его же использует сброс демо-данных.
- Все даты считаются **относительно текущей недели в Europe/Moscow**, без захардкоженных дат, иначе к 28.11 расписание опустеет.
- В расписании есть переносы и замены, субботние пары и разные данные у двух тестовых студентов.
- Данные только вымышленные (см. `fictional-data.md`).

## Тесты
- Vitest, БД — PGlite в памяти, свежая на каждый тестовый файл.
- На каждый эндпоинт: успешный сценарий, 401 без сессии и 404 для чужого ресурса (если у ресурса есть id).
- Смена статуса заявки сотрудником создаёт уведомление студенту, это тоже покрыто тестом.

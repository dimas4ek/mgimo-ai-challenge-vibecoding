# Совместная работа двух Claude Code над проектом

> Этот документ для людей и для Claude. Claude, прочитай его целиком, потом прочитай md-файлы проекта
> (ТЗ, README, ROADMAP, CLAUDE.md) и работай по этим правилам. Где правила расходятся
> с реальностью проекта (стек, команды сборки), предложи правку этого документа, а не обходи его молча.
> Место в репозитории: `docs/AI-COLLAB.md` основного проекта.
>
> **Порядок:** сначала Claude анализирует ТЗ и сам выбирает стек, библиотеки и архитектуру, потом пишет
> `ROADMAP.md` и `CLAUDE.md` проекта (§10, шаг 1). Только после этого ему дают этот документ: он встраивает
> правила в проект и делает подготовку (§13). Стек в этом документе намеренно не зафиксирован.

## 0. Контекст

- Хакатон по вайбкодингу: всю работу делает ИИ. Люди ставят задачу, смотрят результат и пишут правки.
- Два Claude Code, у каждого свой аккаунт и свои лимиты:
  - **`agent:dimas`**: ноут с Arch Linux;
  - **`agent:evv`**: ПК с Windows.
- Код лежит в основном репозитории на GitHub: `dimas4ek/mgimo-ai-challenge-vibecoding`.
- Доска задач лежит в **отдельном приватном репозитории** `dimas4ek/mgimo-ai-challenge-vibecoding-board`, где есть только Issues.
  Основной репозиторий остаётся чистым: код и PR.
- Субагентов для параллельной работы над задачами не используем, чтобы не тратить лимиты.
  Субагент нужен только для ревью (см. §7). Параллельный режим с субагентами описан в §14,
  по умолчанию он выключен.
- Работаем **пачками**, без бесконечного `/loop` (см. §8).

## 1. Главный принцип: сначала контракт

Оба Claude работают одновременно, и один использует код другого, ещё не дописанный. Это возможно только так:

1. Взял задачу, и **первым делом** публикуешь контракт: интерфейсы, классы с сигнатурами, типы,
   doc-комментарии, заглушки (бросают «not implemented» или возвращают фейковые данные, как принято в выбранном языке).
2. Контракт идёт отдельным маленьким PR, который сразу мержится в `main` (сборка должна быть зелёной).
3. После этого второй Claude пишет свой код против этого интерфейса (в тестах использует моки), а ты делаешь реализацию.

Контракт живёт **в коде**, а на доске только ссылка на него. Менять смерженный контракт молча
**запрещено**: сначала комментарий в issue и проверка, кто от него зависит, потом правка всех зависимых мест.

## 2. Доска: `dimas4ek/mgimo-ai-challenge-vibecoding-board`

Работа с доской идёт через `gh` с флагом `-R dimas4ek/mgimo-ai-challenge-vibecoding-board`.

**Labels:**

| Label | Значение |
|---|---|
| `agent:dimas`, `agent:evv` | кто взял задачу |
| `contract-merged` | контракт задачи уже в `main`, от неё можно зависеть |
| `blocked` | ждёт контракт, которого ещё нет |
| `p0` / `p1` / `p2` | приоритет; `p0` — срочные правки от людей |
| `fix` | правка от людей после просмотра результата |
| `proposal` | задачу предложил ИИ, люди ещё не одобрили. Не брать |
| `needs-human` | агент застрял, нужен человек. Не брать |
| `done` | смержено (issue закрывается) |
| `status` | одна закреплённая issue «Статус» (см. §9) |

**Шаблон задачи** (`.github/ISSUE_TEMPLATE/task.md` в репозитории доски):

```
## Что сделать
## Контракт        — что публикуем первым: классы/интерфейсы/сигнатуры и где они лежат
## Зависит от      — #N (нужен только их контракт, не реализация)
## Модуль/пакет    — где работаем (чтобы не пересекаться)
## Готово, когда   — критерии + какие тесты
```

## 3. Какая задача свободна и какую брать

Задача **свободна**, если: issue открыта, нет `agent:*`, нет `blocked`, `proposal` и `needs-human`,
и у всех задач из «Зависит от» стоит `contract-merged`.

**Порядок выбора:**
1. `fix` + `p0`, то есть правки от людей;
2. задачи-блокеры: свободные задачи, от которых зависят другие;
3. по приоритету `p1` → `p2`, при равенстве берём меньший номер;
4. при прочих равных — задачу из «своего» модуля, чтобы меньше конфликтов с напарником.

Заблокированная задача **ни за кем не закреплена**: её берёт тот, кто первым освободится после разблокировки.

## 4. Как взять задачу

**Берёшь по одной задаче.** Следующую берёшь только после того, как предыдущая смержена
(или передана с `needs-human`), даже внутри пачки. Не занимай несколько задач «впрок».

1. `git switch main && git pull`, затем `gh issue list -R dimas4ek/mgimo-ai-challenge-vibecoding-board`.
2. Ставишь свой label `agent:*` и пишешь комментарий `беру (agent:X)`. Label агента в тексте обязателен:
   если две машины работают от одного GitHub-аккаунта, по автору комментария их не различить.
3. Перечитываешь issue. Если там два комментария «беру», задачу получает тот, чей комментарий раньше (`createdAt`).
   Второй снимает свой label и ищет другую задачу.
4. **Перед первым пушем по задаче проверяешь ещё раз:** перечитываешь issue и проверяешь,
   нет ли чужой ветки с этим номером (`git ls-remote origin "*/12-*"`). Если чужой комментарий «беру» раньше
   твоего или чужая ветка уже есть, бросаешь задачу: снимаешь свой label, оставляешь комментарий
   `уступаю (agent:X)` и удаляешь свою ветку.
5. Если задача зависит от контракта, которого ещё нет: не начинаешь её, а ставишь `blocked`
   и комментируешь в issue-зависимости `нужен контракт для #N`. Потом берёшь другую задачу.

## 5. Работа над задачей

- Ветки: `<агент>/<номер>-<кратко>`, например `dimas/12-user-repository`.
- **Шаг 1: контракт.** PR `contract(#12): …`. Он проходит §7 (CI и ревьюер; ревьюер смотрит только сигнатуры
  и соответствие задаче, поэтому это быстро). Мерж → на issue ставишь `contract-merged`.
  Потом снимаешь `blocked` с задач, которые ждали этот контракт, и комментируешь там `контракт готов`.
- **После squash-мержа контракта обычный `git rebase origin/main` даёт конфликт** (проверено). Реализацию
  переносишь так: `git fetch` и `git rebase --onto origin/main <SHA>`, где `<SHA>` — последний коммит контракт-PR
  (`gh pr view <номер PR> --json headRefOid -q .headRefOid`; работает и после удаления ветки).
  Так на новый `main` переезжают только коммиты, сделанные после контракта.
  Контракт-PR мержится **обязательно с `--delete-branch`**: тогда перенесённая ветка пушится обычным `git push`.
  Без этого понадобился бы force-push, который запрещён (§11). Можно и создать новую ветку `<агент>/<номер>-<кратко>-impl`.
- **Шаг 2: реализация и тесты.** PR `#12: …`, в описании `Board: dimas4ek/mgimo-ai-challenge-vibecoding-board#12`.
  В этот же PR входит запись в журнал своего агента `docs/process/<агент>.md`. Этого требует хакатон
  (жюри оценивает процесс работы с ИИ), формат описан в `.claude/rules/process-log.md`.
- PR маленькие, ветки живут недолго. Перед мержем делаешь `git fetch` и rebase на свежий `main`,
  конфликт разбирает тот, кто мержит.
- Перед PR проверяешь, не изменились ли контракты, от которых зависишь.

## 6. Если застрял

CI красный после 2 попыток исправить, контракт напарника не подходит, задача неясна:
ставишь `needs-human`, пишешь в комментарии, что именно не так и какие варианты видишь, снимаешь свой
`agent:*` и берёшь другую задачу. Не крутишься на месте и не тратишь на это лимит.

## 7. Ревью и мерж (без людей)

PR мержится, когда выполнены оба условия:
1. **CI зелёный** (`gh pr checks <PR> --watch --interval 10`). Сразу после пуша CI может ещё не появиться
   (`no checks reported`): тогда просто повтори команду (проверено: так бывает почти каждый раз);
2. **субагент-ревьюер одобрил.** Ревьюер описан в `.claude/agents/pr-reviewer.md`, работает на `model: sonnet`,
   ему доступны только чтение и `git`/`gh`. Он сверяет PR с задачей, контрактами и тестами.
   Нашёл проблемы → исправляешь. Максимум 2 круга, потом `needs-human`.

Мерж: `gh pr merge --squash --delete-branch`. Если включена защита веток, то с `--auto`.
После мержа закрываешь issue с `done` и обновляешь «Статус».

## 8. Режим работы: пачки

- Одна пачка = до 2–3 задач, которые берутся **по одной** (§4), потом **стоп и отчёт**.
- Перед каждой пачкой `/clear` или новая сессия: контекст свежий и дешёвый, всё нужное есть в этом документе и на доске.
- **Свободных задач нет, но есть заблокированные, чей контракт кто-то сейчас делает → ждём.**
  Ждёт скрипт `.claude/scripts/wait-task.mjs` в фоне: раз в минуту смотрит доску, выходит, как только
  задача освободилась (тогда берём её), и сдаётся через 90 минут. Сам Claude доску по кругу не опрашивает:
  это тратило бы лимит.
- **Ждать нечего → сразу стоп и отчёт.** Так бывает, когда открытых задач нет, все заняты или
  заблокированные ждут задач с `needs-human`/`proposal`, то есть людей.
- Пачку запускает человек одной фразой (см. §12). Между пачками он смотрит отчёт и демо.
- Не запускайте пачки у обоих в одну и ту же секунду: в тесте оба Claude сразу выбрали одну и ту же задачу.
  Протокол §4 это разрулит, но разница даже в полминуты снимает гонку почти полностью.

**Формат отчёта в конце пачки:**

```
Сделано:        #N — что (PR-ссылка), …
В работе у напарника: #N …
Заблокировано:  #N ждёт контракт #M (у кого)
Нужен человек:  #N — почему
Дальше:         что логично делать следующей пачкой
```

## 9. Issue «Статус»

Одна закреплённая issue с label `status`. После каждого мержа её **тело пересобирается целиком**
из текущего состояния доски (`gh issue edit --body`), а не дописывается. Так одновременные
обновления от двух Claude ничего не ломают. В ней перечислено: что готово, что в работе и у кого,
что заблокировано, что ждёт людей.

## 10. Планирование

- **Шаг 1: анализ ТЗ** (Claude `agent:dimas`, до этого документа). Claude выбирает стек, библиотеки и версии,
  архитектуру и модули, пишет `ROADMAP.md` и `CLAUDE.md` проекта. Команды сборки, тестов и запуска
  записываются в `CLAUDE.md`, и дальше все пользуются только ими. Правила под выбранный стек
  (стиль кода, тесты, архитектура) раскладываются в `.claude/rules/*.md`. Правила, которые касаются
  только части проекта, привязываются к её путям. `CLAUDE.md` остаётся коротким. Люди одобряют результат.
- **Шаг 2: разбиение на задачи делает только Claude `agent:dimas`, один раз.** Он делит проект на задачи
  с контрактами и зависимостями, стремясь к тому, чтобы как можно больше задач можно было начать сразу
  (сначала контракты-основы, потом остальное), и по модулям разводит работу двух агентов.
  Список показывает человеку и после ОК заводит на доске.
- Новые фичи по ходу работы ИИ заводит с `proposal`, а люди снимают label, если одобряют.
- Правки людей заводятся с `fix` + `p0`. Человек может написать issue сам или попросить своего Claude: «заведи fix: …».

## 11. Окружение (Arch + Windows)

- `.gitattributes`: `* text=auto eol=lf`, чтобы не было диффов из-за CRLF.
- Стек выбирается на шаге 1 (§10). При выборе важно, чтобы всё работало и на Windows, и на Linux:
  сборщик с обёрткой или скрипты, которые запускаются на обеих ОС. Версии рантайма и инструментов
  зафиксированы в репозитории, у обоих они одинаковые.
- **CI на GitHub Actions — единственный судья:** если локально собирается, а в CI нет, прав CI.
- `CLAUDE.local.md` на каждой машине (в `.gitignore`), например:
  `Я — agent:dimas. ОС: Arch Linux. Доска: dimas4ek/mgimo-ai-challenge-vibecoding-board.`
- Разрешения: allowlist в `.claude/settings.json` (`git`, `gh issue`, `gh pr`, `gh label`, команды сборки и тестов)
  или auto mode. `bypassPermissions` не включать. `git push --force` и прямой пуш в `main` запрещены
  жёстко, через `deny` (§13, пункт 7).
- **Как писать Bash-команды** (правило в `CLAUDE.md` проекта; проверено в тесте). Без переменных оболочки
  (`B=…`, `$B`) и многострочных скриптов. Адрес доски всегда полностью. Одна команда или цепочка через `&&`.
  Без `;`, `|`, `$( … )`. Иначе allowlist их не узнаёт: в режиме без вопросов команда отклоняется,
  а в обычном режиме Claude дёргает человека за разрешением.
- **Первый запуск Claude в папке проекта — подтвердить диалог доверия.** Пока папка не доверенная, Claude молча
  игнорирует разрешения из `.claude/settings.json`. Касается обоих, на каждой машине.
- **Всё, на что опирается работа, лежит в репозитории** (`CLAUDE.md`, `.claude/rules`, `skills`, `agents`,
  `settings.json`). Личные `~/.claude` у людей разные (например, у dimas стоят глобальные плагины, а у evv нет),
  поэтому правила проекта не должны ссылаться на чужие личные skills и плагины.

## 12. Фразы для людей

Каждую фразу человек пишет своему Claude. Перед каждой пачкой нужен `/clear` или новая сессия.
После подготовки (§13, пункт 4) у части фраз появляется короткая команда, она указана в скобках.

### Старт (один раз)

- **Анализ ТЗ** (dimas, до этого документа):
  `Прочитай ТЗ (<файл>). Выбери стек, библиотеки и архитектуру, обоснуй выбор. Напиши ROADMAP.md, короткий CLAUDE.md с командами сборки, тестов и запуска и правила под стек в .claude/rules/. Покажи мне до коммита.`
- **Подготовка** (dimas):
  `Прочитай <путь к AI-COLLAB.md> и <путь к PHRASES.md>, положи их в docs/ и сделай подготовку по §13, взяв за основу шаблоны из <путь к collab-template>. Сначала покажи список того, что создашь на GitHub.`
- **Разбиение на задачи** (dimas):
  `Разбей проект на задачи по §10, шаг 2. Покажи список, после моего ОК заведи их на доске.`
- **Первый запуск у evv** (после clone/pull):
  `Прочитай docs/AI-COLLAB.md и CLAUDE.md. Сделай пункты «Делает evv» из §13 (CLAUDE.local.md: я — agent:evv, Windows) и проверь сборку.`

### Работа (оба, по кругу)

- **Пачка** (`/batch`):
  `Пачка по docs/AI-COLLAB.md: по одной бери и делай до 3 свободных задач с доски, мержи, обнови Статус и остановись с отчётом.`
- **Пачка в параллельном режиме** (`/batch parallel`; только если люди решили его включить, §14).
  ⚠ Лимит тратится примерно в 3 раза быстрее, конфликтов при слиянии больше. Включать, только если на доске
  много свободных независимых задач и лимита заметно больше, чем нужно. Режим действует только на одну пачку:
  `Пачка в параллельном режиме по §14: до 2 субагентов, каждый на одну свободную независимую задачу. Когда все закончат, остановись с отчётом.`
- **Посмотреть состояние** (`/board`; ничего не меняет):
  `Покажи состояние доски: что готово, что в работе и у кого, что заблокировано, что ждёт людей. Ничего не меняй.`
- **Посмотреть результат:**
  `Обнови main, собери и запусти проект командами из CLAUDE.md и скажи, как посмотреть результат.`

### Управление задачами

- **Правка после просмотра** (`/fix <текст>`):
  `Заведи на доске fix p0: <что не так и как должно быть>.`
- **Новая фича** (`/proposal <текст>`):
  `Заведи на доске proposal: <что нужно и зачем>. Разбей на задачи с контрактами по §10.`
- **Одобрить предложения:**
  `Одобряю #<номер>, #<номер>: сними с них proposal.` (или `Отклоняю #<номер>: закрой с комментарием <почему>.`)
- **Разобрать needs-human:**
  `Покажи задачи с needs-human и предложи варианты решения для каждой.`
  затем `По #<номер> делаем так: <решение>. Запиши это в issue и сними needs-human.`
- **Сменить приоритет:**
  `Поставь #<номер> приоритет <p0 / p1 / p2>.`
- **Изменить контракт:**
  `Нужно изменить контракт из #<номер>: <что меняем и почему>. Найди всё, что от него зависит, и сделай по правилам §1.`

### Особые ситуации

- **Лимит на исходе:**
  `Лимит на исходе: доделай текущую задачу, новых не бери, отчитайся.`
- **Сменить правила работы:**
  `Меняем правило: <какое правило и как теперь>. Обнови docs/AI-COLLAB.md, CLAUDE.md и затронутые skills/rules отдельным PR.` Второму после этого нужно сделать `git pull` и `/clear`.
- **Подготовка к сдаче:**
  `Готовимся к сдаче: проверь, что main собирается и тесты зелёные, обнови README (что сделано, как запустить), перечисли незакрытые задачи.`

2. [ ] Добавить напарника collaborator'ом в оба репозитория.
3. [ ] В основном репозитории:
   - `docs/AI-COLLAB.md` (этот файл) и `docs/PHRASES.md` (шпаргалка фраз для людей);
   - короткий раздел в `CLAUDE.md` со ссылкой на него;
   - `.gitattributes`, `.claude/settings.json` (allowlist);
   - `.claude/agents/pr-reviewer.md`;

## 14. Параллельный режим (опционально, по умолчанию выключен)

Включается **только явной фразой человека** (§12) и **только на одну пачку**. Без неё действует §0: субагенты
нужны только для ревью.

- **Claude становится бригадиром.** Он запускает до N субагентов (по умолчанию 2), каждого в своём git worktree
  со своей веткой. Один субагент делает одну задачу.
- **Правило «по одной» из §4 здесь означает одну задачу на исполнителя.** Бригадир занимает задачи по одной,
  по полному протоколу §4, и ровно столько, сколько субагентов запускает. Впрок задачи не занимаются.
- **Параллельно идут только независимые задачи:** они не зависят друг от друга и лежат в разных модулях.
- **С доской работает только бригадир:** labels, комментарии, «Статус». Субагенты коммитят и пушат
  только в свою ветку. Контракт по-прежнему идёт первым: бригадир мержит контракт-PR сразу, как только он готов.
- **Постановка субагенту полная:** текст issue, пути к контрактам, команды из `CLAUDE.md`, критерии готовности.
  Переспросить субагент не может. Если он застрял, то возвращает отчёт, а бригадир ставит `needs-human` (§6).
- **Цикл:** субагент закончил → бригадир делает ревью (§7) → мерж → только потом бригадир занимает
  следующую задачу на освободившееся место.
- Label остаётся по машине (`agent:dimas` / `agent:evv`). В комментарии бригадир пишет, кто делает задачу:
  `беру (субагент 2, ветка dimas/14-…)`.
- **Расход лимита примерно в (N+1) раз больше.** Если лимит заканчивается, доделываем начатое,
  новые задачи не берём и возвращаемся к обычному режиму.
